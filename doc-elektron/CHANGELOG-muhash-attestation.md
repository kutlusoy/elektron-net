# Changelog: MuHash UTXO Attestation (Phase 1 + Activation Gate)

**Status:** Implemented on branch `MuHash`. Active on **testnet/testnet4/regtest only** (low, explicit activation heights); permanently disabled on **mainnet** (`MuhashAttestationActivationHeight = -1`) until a separate, deliberate decision is made to activate it there.
**Related:** `doc-elektron/fix-report-utxo-attestation-scalability.md` (design + rationale), `BITCOIN_CORE_DIFF.md` §2.2 (consensus rule summary).
**Scope of this pass:** Fix-report Phase 1 (incremental accumulator, consensus hooks, persistence, mining path) + Phase 3 (per-network activation height gate). Phase 2 (embedding the accumulator in checkpoint snapshot metadata) and the optional Phase 4 (P2P protocol-version peer gate) are **not** included here — see "Deferred" below.

This file is a dated, chronological log of the changes made in this pass, in the spirit of `BITCOIN_CORE_DIFF.md` (which records the *current-state* diff against upstream Bitcoin Core; this file records *how* the MuHash attestation change was built, one step at a time, so the history stays reviewable after the fact).

## 2026-07-01

**New consensus parameter.** `Consensus::Params::MuhashAttestationActivationHeight` (`src/consensus/params.h`), same `-1`-disabled sentinel convention as the existing `MinDifficultyActivationHeight`. Set per network in `src/kernel/chainparams.cpp`:
- Mainnet: `-1` (disabled — explicit, will not change as a side effect of this pass).
- Testnet / Testnet4: `5000` (revised same-day from an initial `50000` placeholder — the network is confirmed still near height 0, so `5000` gives a real testing window without an unnecessarily long wait; **still verify against the live tip before deployment** if time has passed).
- Regtest: `50` (revised same-day from an initial `10` — high enough to leave a visible pre-activation window for manual testing, still fast for CI).

**Checkpoint interval made per-network too.** The existing automatic-UTXO-snapshot / P2P-bootstrap checkpoint interval (previously the single hardcoded global `MANDATORY_PRUNE_DEPTH = 197280` in `src/validation.h`, used directly by `WriteAutomaticSnapshot`, `ValidateUTXOCheckpoint`'s log-level split, `Chainstate::GetPruneRange`, and several `net_processing.cpp` snapshot-bootstrap calculations) is now a new `Consensus::Params::MandatoryPruneDepth` field (default `197280`, matching the still-present `MANDATORY_PRUNE_DEPTH` constant, which now only serves as that default/mainnet reference value — not something requested by the original fix report, but needed so the checkpoint/snapshot cycle can actually be exercised while testing MuHash activation on testnet/regtest, rather than only after 197,280 blocks). All 9 real (non-comment) call sites already had `Consensus::Params`/`ChainstateManager` access in scope, so this was a mechanical read-from-params change, not a redesign. Per network:
- Mainnet: `197280` (unchanged).
- Testnet / Testnet4: `7000`.
- Regtest: `100`.

`nPruneAfterHeight` (`src/kernel/chainparams.cpp`) was initially left untouched, then corrected the same day (see the second dated entry below) to match `MandatoryPruneDepth` per network, mirroring the mainnet principle where the two are already equal (`197280` == `197280`).

**New incremental UTXO MuHash accumulator.** `src/kernel/utxo_muhash.h`: `kernel::UTXOMuHashState`, a thin wrapper around the existing `MuHash3072` type (`src/crypto/muhash.h`) that reuses the existing `ApplyCoinHash`/`RemoveCoinHash` helpers (`src/kernel/coinstats.cpp`) already used by `CoinStatsIndex` — no new per-coin serialization logic was written.

**Persistence.** `src/txdb.h`/`.cpp`: `CCoinsViewDB::WriteUTXOMuHashState`/`ReadUTXOMuHashState`, new DB key `DB_UTXO_MUHASH` (`'U'`). The accumulator is stored together with the chain tip hash it corresponds to, so a stale or missing entry (first run of this feature on an existing chainstate, or a crash between this write and the coins DB flush) is detected on load and triggers a one-time rebuild rather than silently using wrong data.

**Chainstate wiring.** `src/validation.h`/`.cpp`:
- `Chainstate::m_utxo_muhash` + `Chainstate::UTXOMuHash()` accessor, `Chainstate::EnsureUTXOMuHashLoaded()` (lazy load-or-cold-start-rebuild, called once per chainstate).
- `ConnectBlock()`: loads the accumulator at the top of the function (so it represents the state *before* the candidate block, matching what `ComputeBlockUTXOAttestationHash` expects as its base); commits this block's coin changes to it only after the `fJustCheck` early-return *and* after `WriteBlockUndo` succeeds — so speculative/dry-run connects (mining, `TestBlockValidity`) and disk-write failures never mutate the persistent accumulator, only blocks that are actually, successfully connected do.
- `DisconnectBlock()`: applies the exact inverse (`RemoveCoin` for the disconnected block's own outputs, `AddCoin` for restored inputs, read back from the view after `ApplyTxInUndo` rather than trusting the raw undo record, so it always matches what was actually restored).
- `FlushStateToDisk()`: persists the accumulator right after `CoinsTip().Flush()/Sync()`, keyed to the same best-block hash.
- The accumulator tracking itself is **unconditional** (runs on every block regardless of activation height), so it is already fully warmed up by the time the activation height is reached — only *consuming* it for the consensus attestation value is height-gated.

**Consensus switch.** `ComputeBlockUTXOAttestationHash()` (`src/validation.cpp`) now takes the consensus params and a pointer to the current accumulator. Post-activation, it clones the accumulator (cheap — a few hundred bytes) and applies only the candidate block's own coin changes, instead of a full `HASH_SERIALIZED` rescan of the entire UTXO set. Pre-activation (and on mainnet, always) behavior is byte-for-byte unchanged from before this pass.

**Mining path.** `src/node/miner.cpp` `CreateNewBlock()`: passes the new parameters through; post-activation this removes the double full-UTXO-set simulation that previously happened on every mined block (once for the template, once again for validation).

**Tests.**
- Unit (`src/test/elektron_simulation.cpp`): `muhash_accumulator_matches_full_scan` (incremental accumulator == from-scratch full `MUHASH` scan), `muhash_accumulator_survives_reorg` (disconnecting blocks returns the accumulator to the exact prior state). The pre-existing `checkpoint_and_snapshot_mechanism` test was adjusted to compute its expected attestation via the production `ComputeBlockUTXOAttestationHash()` function instead of hardcoding `HASH_SERIALIZED`, so it stays valid regardless of whether regtest's activation height has been reached.
- `src/test/miner_tests.cpp`: updated call site for the new function signature.
- Functional (`test/functional/feature_muhash_attestation_activation.py`, registered in `test_runner.py`): mines across the activation height, forces a reorg that straddles it, restarts the node (accumulator persistence / cold-start), and checks `getblocktemplate`'s `coinbase_required_outputs` keeps its existing 32-byte-hash shape throughout — a practical (not just code-inspection) confirmation that mining pools following the documented GBT contract (`mining-pool-integration.md`, `BITCOIN_CORE_DIFF.md` §9.1) need no changes.

**Miner/pool impact assessment.** Re-verified before implementation: `kutlusoy/elektron-net-pool` contains no code that computes or independently verifies the UTXO attestation hash (confirmed via repository code search for `attestation`/`muhash`/`utxo`/`hash_serialized` — zero matches). Pools only copy the `scriptPubKey` from `getblocktemplate`'s `coinbase_required_outputs`, and that field's shape (32-byte hash, same OP_RETURN encoding) is unchanged by this switch. No changes needed in the pool, pool-ui, or faucet repositories for this pass.

**Documentation.** `doc-elektron/fix-report-utxo-attestation-scalability.md` status field updated; `BITCOIN_CORE_DIFF.md` §2.2 updated to describe the dual-algorithm behavior and the new consensus parameter, "Last updated" bumped.

## 2026-07-01 (same day, follow-up: `nPruneAfterHeight` + live pruning verification)

Live-tested this branch end-to-end on a real regtest node (build + run `elektrond`/`elektron-cli`, mine across both boundaries, restart, `pruneblockchain`) rather than relying on unit/functional tests alone. Two findings:

1. **`nPruneAfterHeight` was inconsistent with the new `MandatoryPruneDepth`.** Mainnet already has them equal (`197280` == `197280`, "pruning starts at the first checkpoint" per §2.1). Testnet/testnet4 still had the old `nPruneAfterHeight = 1000` (vs. `MandatoryPruneDepth = 7000`) and regtest had `opts.fastprune ? 100 : 1000` (vs. `MandatoryPruneDepth = 100`) — meaning pruning eligibility wouldn't even be *considered* until height 1000, well past the point the checkpoint/attestation testing is meant to happen around. Fixed to match `MandatoryPruneDepth` on all three networks (testnet/testnet4: `7000`; regtest: fixed `100`, dropping the `fastprune` conditional since both branches now agree).
2. **Confirmed via live test that actual block-*file* deletion additionally requires `-fastprune`.** Height-based eligibility (`GetPruneRange`) is necessary but not sufficient: `FindFilesToPrune` only deletes whole `blk*.dat`/`rev*.dat` files, and a file only rolls over to the next number once it hits `MAX_BLOCKFILE_SIZE` (128 MiB) — `-fastprune` lowers that to 64 KiB (`src/node/blockstorage.cpp`), which is what actually makes multiple block files (and therefore observable pruning) reachable within a short regtest session with realistically tiny empty blocks. Without `-fastprune`, a regtest node would need ~400,000+ blocks before a second file is ever created, regardless of how low `MandatoryPruneDepth`/`nPruneAfterHeight` are. Not a bug — this is pre-existing, correct Bitcoin Core behavior — but worth recording since it wasn't obvious from the code alone and is essential to reproducing a working pruning test.

Verified live with the corrected `nPruneAfterHeight` values: fresh regtest node, `-fastprune`, mined to height 600. `pruneblockchain 500` (and automatic pruning during normal flushes) correctly capped the actual prune height at `tip - MandatoryPruneDepth` (pruned to height ~433, since pruning only removes whole files and the eligible cutoff of 500 didn't land exactly on a file boundary) and **physically deleted** the old `blk00000.dat`/`blk00001.dat`/`rev00000.dat`/`rev00001.dat` file pairs from disk — only the current file (`blk00002.dat`/`rev00002.dat`) remained. `getblockchaininfo` reported `pruneheight: 433` afterwards, confirming the RPC-visible state matches the on-disk reality.

## 2026-07-01 (same day, critical fix: P2P snapshot-bootstrap messages were wire-broken on every network)

**Not part of the MuHash change itself, but found while verifying it end-to-end**, and severe enough to fix immediately per the user's request. Two-node live test: node A mined to height 1100 (`-fastprune`, `MandatoryPruneDepth=100`) and pruned (`pruneheight=865`, matching the user's own independently-reproduced regtest run). Node B connected fresh via real P2P (`-connect`), synced headers to 1100/1100 immediately, but **stayed stuck at `blocks: 0` indefinitely** — the exact symptom the user reported and asked about ("Funktioniert der sync ... nach dem pruning und snapshot wirklich?").

**Root cause**, found with `-debug=net` on both nodes:
```
Node B: [net] sending getutxosnapshot (32 bytes) peer=0
Node A: [net] received: getutxosnaps (32 bytes) peer=0
Node A: [net] Unknown message type "getutxosnaps" from peer=0
```
`NetMsgType::GETUTXOSNAPSHOT` (`src/protocol.h`) was defined as the string `"getutxosnapshot"` — **15 characters**, exceeding `CMessageHeader::MESSAGE_TYPE_SIZE` (12 bytes), a long-standing Bitcoin P2P wire-protocol constant every message type name must fit in (all of Bitcoin's own message names are ≤12 chars: `getheaders`, `sendheaders`, etc.). `NetMsgType::GETSNAPSHOTDATA` (`"getsnapshotdata"`, also 15 chars) had the same problem; `UTXOSNAPSHOT`/`SNAPSHOTDATA` (both exactly 12 chars) were fine.

Two different failure modes depending on transport, both traced in the source:
- **V2 (BIP324) transport — silent corruption, not just truncation.** `V2Transport::SetMessageToSend` (`src/net.cpp:1504-1506`) allocates a fixed 12-byte slot for the type string and `std::copy`s the full type string into it with **no length check** — for a 15-character name this overflows into the payload's first 3 bytes. The receiver reads back a mangled 12-byte type (`"getutxosnaps"`), fails to match any known handler, and silently drops the message. This is what happened in the live test (peer connected with `transport: v2`).
- **V1 (legacy) transport — hard crash.** `CMessageHeader::CMessageHeader` (`src/protocol.cpp:10-19`) has `assert(msg_type[i] == 0)` after copying up to `MESSAGE_TYPE_SIZE` bytes — a >12-char message type triggers an **assertion failure**, i.e. any node that ever tried to send `GETUTXOSNAPSHOT`/`GETSNAPSHOTDATA` over a V1 connection would have crashed outright.

Net effect: **the entire P2P UTXO-snapshot bootstrap mechanism (§2.3 of `BITCOIN_CORE_DIFF.md`) has never worked, on any network** (mainnet/testnet/testnet4/regtest — this is a wire-protocol constant, not chainparams-dependent) — a pruned node has had no way to serve a fresh peer past its prune point since this feature was written, and any V1 peer that tried would crash.

**Fix** (`src/protocol.h`): shortened both names to fit the 12-byte limit — `GETUTXOSNAPSHOT`: `"getutxosnapshot"` → `"getutxosnap"` (11 chars), `GETSNAPSHOTDATA`: `"getsnapshotdata"` → `"getsnapdata"` (11 chars). No other code changes needed: all call sites reference the `NetMsgType::` C++ constants, not the raw strings, so this is a self-contained, minimal fix. `UTXOSNAPSHOT`/`SNAPSHOTDATA` left unchanged (already valid).

**Re-verified live with the fix**, same two-node setup (node A pruned past height 865, tip 1100; fresh node B connecting via P2P) — the message now arrived intact, but this uncovered five more, previously entirely untested, bugs in the same P2P snapshot-bootstrap path (§2.3 `BITCOIN_CORE_DIFF.md`). Each was found, fixed, and re-verified live before moving to the next, per the user's "sofort beheben und protokollieren" instruction. All five are below, in the order they were hit.

### Bug 2: `GETUTXOSNAPSHOT` handler used `cs_main`-protected data without holding `cs_main`

After the bug-1 fix, node A crashed processing node B's (now correctly-named) request:
```
Assertion failed: lock cs_main not held in ./node/blockstorage.cpp:213
```
The `GETUTXOSNAPSHOT` handler in `src/net_processing.cpp` called `m_chainman.m_blockman.LookupBlockIndex(checkpoint_hash)` with no lock held. Fixed by wrapping the lookup in a scoped `LOCK(cs_main)` block, extracting just the two booleans/height needed (`checkpoint_height`, `is_checkpoint`) before releasing the lock — the same pattern already used by other message handlers in the same file (e.g. `GETBLOCKS`).

### Bug 3: `SNAPSHOTDATA` receiver left an `AutoFile` open across a scope its destructor can't tolerate

After the bug-2 fix, node B (the receiver of snapshot chunks) crashed:
```
./streams.h:401 AutoFile::~AutoFile(): Assertion 'IsNull()' failed.
```
`AutoFile`'s destructor asserts the file was explicitly closed if anything was written to it (`m_was_written`). Of the four `AutoFile` usages in `net_processing.cpp`'s snapshot code, only the one in the `SNAPSHOTDATA` handler (writing a downloaded chunk to the temp file) was missing an explicit `.fclose()` before the object went out of scope and before the subsequent `fs::rename()` of the completed file. Fixed by adding the `.fclose()` call (with a warning log if it fails) right after the write, before checking `AddRange`/renaming.

### Bug 4: `MaybeActivateAutomaticSnapshot` also used `cs_main`-protected data without holding `cs_main`

After the bug-3 fix, node B crashed again with the *same* assertion message as bug 2 (`lock cs_main not held ... blockstorage.cpp:213`), but from a different call site — the plain assertion text doesn't include a backtrace, so this needed `gdb -batch -x cmds.txt ./bin/elektrond` (`run <args>`; `bt`; `thread apply all bt`; `quit`) to identify. The backtrace showed `MaybeActivateAutomaticSnapshot` (`src/init.cpp`), called from a `CScheduler::Repeat` wrapper — i.e. this function runs every 30 seconds for as long as the node is in IBD, not just once at startup as an earlier grep-only read had assumed. It had the same unlocked `LookupBlockIndex` call as bug 2. Fixed the same way: `WITH_LOCK(::cs_main, return chainman.m_blockman.LookupBlockIndex(...))`.

### Bug 5: automatic snapshot activation was not idempotent — retried every 30s, crashing on the second attempt

After the bug-4 fix, node B crashed a third time, differently:
```
Fatal LevelDB error: IO error: lock /tmp/node-b/regtest/chainstate_snapshot/LOCK: already held by process
```
`MaybeActivateAutomaticSnapshot` runs every 30 seconds while `IsInitialBlockDownload()` is true, which it can remain for a while even *after* a successful activation. The function had no guard against re-activating an already-activated snapshot, so the very next scheduled run tried to open a second LevelDB handle on the same `chainstate_snapshot/` directory the first (still-open) activation already held.

Two fix attempts were tried and **both failed live** before landing on the working one:
1. Checking `chainman.CurrentChainstate()->m_from_snapshot_blockhash` before attempting activation — rebuilt, retested, crashed identically on the next 30s cycle (the debug.log still showed a second "attempting activation" line).
2. Checking `chainman.ActiveChain().Tip()`'s height/hash against the snapshot filename — same result, still crashed.

Both approaches relied on introspecting `ChainstateManager`'s current chainstate selection, which (as bug 6 below makes clear in hindsight) was not behaving as expected at this point in the investigation. The working fix instead avoids chainstate introspection entirely: a function-local `static uint256 s_activated_snapshot_hash` (safe because this function has exactly one production call site and is never invoked from unit tests) is checked against the hash parsed out of the snapshot filename (`<height>-<hash>.dat`) before attempting activation, and set immediately after `ActivateSnapshot()` succeeds. Rebuilt, retested — held stable through 3+ scheduler cycles (~180s) with no re-activation attempt and no crash.

### Bug 6: successful activation still left the node reporting `blocks: 0` forever

With bugs 1–5 fixed, node B no longer crashed, and the snapshot activated exactly once — but `getblockchaininfo`/`getblockcount` stayed stuck at `blocks: 0`, `initialblockdownload: true`, `bestblockhash` = genesis, indefinitely, even though the debug.log clearly showed `"[snapshot] Successfully activated snapshot at height 1100"`. This is very likely the actual mechanism behind the user's original bug report (a second GUI peer "stuck, not syncing" after pruning/snapshots) — the message-truncation bug (bug 1) meant that scenario never even got this far before, so this bug was previously unreachable and untested.

First hypothesis (wrong, tried and reverted): that `ActivateSnapshot()` never called `ActivateBestChain()` on the new chainstate, so its tip was never actually moved to the snapshot block. Adding an explicit `chainman.ActivateBestChains()` call after activation was rebuilt and retested — **no change**, still stuck at `blocks: 0`. This ruled out that theory: `PopulateAndValidateSnapshot()` already calls `snapshot_chainstate.m_chain.SetTip(*snapshot_start_block)` directly, so the snapshot chainstate's own tip was correct all along.

**Actual root cause:** `MaybeActivateAutomaticSnapshot` (`src/init.cpp`), after a successful activation, called `chainman.HistoricalChainstate()->SetTargetBlock(nullptr)` to abandon the now-useless old (pre-snapshot) IBD chainstate — background validation can never complete for it since the historical blocks it would need are pruned on every peer. But `ChainstateManager::CurrentChainstate()` (`src/validation.h`) selects the *first* chainstate in `m_chainstates` that has no `m_target_blockhash` — and `m_chainstates` is ordered `[old IBD chainstate, new snapshot chainstate]` (`AddChainstate()` appends the new one to the end). Clearing the IBD chainstate's target left *both* chainstates target-less, so `CurrentChainstate()` — and therefore `ActiveChainstate()`, and therefore every RPC that reports chain height — kept resolving to the old, still-at-genesis IBD chainstate instead of the snapshot chainstate, forever.

Fix: instead of merely clearing the old chainstate's target, delete it outright via `chainman.DeleteChainstate()` — the same cleanup already used a few lines earlier in `ChainstateManager::ActivateSnapshot()` when replacing an old snapshot with a newer one (`src/validation.cpp` ~line 6003). Deleting it removes the ambiguity completely: only the snapshot chainstate remains, so `CurrentChainstate()` resolves to it unambiguously.

This surfaced a second, latent bug in `ChainstateManager::DeleteChainstate()` itself (`src/validation.cpp` ~line 6663): it unconditionally dereferenced `prev_chainstate->m_mempool->size()`, assuming the chainstate being deleted currently owns the mempool. That assumption holds when deleting an old *snapshot* chainstate (which does hold the swapped-in mempool at that point) but not for the old IBD chainstate here, whose mempool was already swapped away to the new snapshot chainstate inside `AddChainstate()` during activation — leaving it `nullptr`. In this Debug build (asserts active), this would have been a null-pointer dereference. Fixed by only performing the mempool hand-off when `prev_chainstate->m_mempool` is non-null; the pre-existing (snapshot-replacement) call site is unaffected since its mempool is always present.

**Final live verification** (all six fixes together): fresh two-node regtest run, node A at height 1100 (pruned to 865), node B connecting cold via real P2P. Node B: synced headers instantly, requested and downloaded the snapshot, activated it in a single attempt (`grep -c "attempting activation" debug.log` → `1`), logged `"[snapshot] Discarded old pre-snapshot chainstate"`, and `getblockchaininfo` correctly reported `"blocks": 1100` with `bestblockhash` identical to node A's tip. No crashes, no warnings, no errors in either node's `debug.log` or stderr across the full test.

## 2026-07-02 (follow-up: three more bugs found via user-reported Windows crash)

The user ran a fresh Windows GUI node (`elektron-qt.exe`) against this branch and hit two crashes back to back, reported via screenshots: an assertion failure (`validation.cpp:5656`, inside `ChainstateManager::CheckBlockIndex()`) after an automatic snapshot activated and new blocks kept arriving, followed by a restart producing a clean-looking but fatal error dialog: *"Für den angegebenen Blockhash '...' wurden keine Assumeutxo-Daten gefunden"* ("No assumeutxo data found for the given blockhash"). Reproduced and fixed live on Linux, per the user's "sofort beheben und protokollieren" instruction — this uncovered a further two bugs (8 and 9) while verifying the fix for the first.

### Bug 7: `m_chain_tx_count` was never set for automatic/dynamic snapshots, because they have no static chainparams entry

Root cause, common to both of the user's crashes: real (upstream) assumeutxo snapshots have a hardcoded `AssumeutxoData` entry per snapshot height in chainparams (`GetParams().AssumeutxoForHeight()`/`AssumeutxoForBlockhash()`). Elektron's automatic snapshots are *dynamic* — their heights are computed at runtime from `Consensus::Params::MandatoryPruneDepth`, never hardcoded — so that lookup always returns nothing (`au_data` is always `std::nullopt`) for one of ours. Two places assumed it would always be present:

- `ChainstateManager::PopulateAndValidateSnapshot()` (`src/validation.cpp`) only set `index->m_chain_tx_count` (the snapshot base block's transaction-count-from-genesis) `if (au_data)`. Left at its default `0`, `CBlockIndex::HaveNumChainTxs()` (`m_chain_tx_count != 0`) is `false` for the snapshot base — which violates an invariant `ChainstateManager::CheckBlockIndex()` asserts on every call: `(pindexFirstNeverProcessed == nullptr || pindex == snap_base) == pindex->HaveNumChainTxs()`. Regtest defaults `-checkblockindex` to run on *every* validation operation, and `CheckBlockIndex()` re-runs on every new header accepted — so the very next block header to arrive after activation reliably crashed the node. This is exactly the user's first screenshot.
- `BlockManager::LoadBlockIndex()` (`src/node/blockstorage.cpp`), called on every startup when a snapshot chainstate exists on disk, treated a missing `au_data` as fatal and refused to start at all: *"Assumeutxo data not found for the given blockhash"*. Since `au_data` is *always* missing for our automatic snapshots, this meant **every single restart of a node that had ever activated one** hit this fatal error — not an edge case. This is the user's second screenshot.

Fix: both call sites now branch on whether `au_data` is present. When it is (a real, static assumeutxo snapshot), behavior is unchanged. When it isn't (one of ours), `m_snapshot_height` is derived directly from the already-loaded block index (no static table needed for that), and `m_chain_tx_count` is set to a `base_height + 1` lower-bound estimate (one tx per block) — this value only feeds the `verificationprogress` display, never consensus validity, and the true historical count is unknowable at a pruned/snapshot-bootstrapped node anyway.

### Bug 8: automatic snapshots were silently captured one block too early (off-by-one), corrupting checkpoint data after MuHash activation

Found while re-verifying bug 7's fix with continued mining past a checkpoint (needed to actually re-trigger `CheckBlockIndex()` post-activation). Once bug 7 no longer crashed the node, mining 20 more blocks on the source node made the bootstrapped node reject the very next block after the checkpoint:
```
ConnectTip: ConnectBlock ... failed, bad-utxo-attestation, UTXO attestation mismatch at height 1101: expected 20505b7d..., got 792abd9f...
```
Root cause: `WriteAutomaticSnapshot()` used to be called from inside `Chainstate::ConnectBlock()`, which runs *before* `ConnectTip()`'s `view.Flush()` merges the connecting block's own coin changes out of the per-block `m_connect_block_view` cache and into `CoinsTip()`. `WriteAutomaticSnapshot()` reads the checkpoint's coin data from `CoinsDB()`, reached via its own internal `ForceFlushStateToDisk()` (which flushes `CoinsTip()` → `CoinsDB()`) — at that point in `ConnectBlock()`, `CoinsTip()` still only reflected the *parent* block's state, so the checkpoint block's own coinbase output was silently missing from every snapshot file. Confirmed directly from node A's own logs: before the fix, the height-1000 checkpoint reported `coins=999`; the height-1100 checkpoint reported `coins=1099`. After the fix, height-1100 correctly reports `coins=1100`.

Every bootstrapping peer rebuilds its MuHash accumulator from a cold start via a full scan of the received snapshot coins (`Chainstate::EnsureUTXOMuHashLoaded()`) — a mathematically exact substitute for the incrementally-tracked value *only if the underlying coin set is actually complete*. A snapshot missing one coin produces an accumulator that's wrong by exactly that coin, which is invisible until the very next block's attestation is checked against it. This is likely the deeper reason behind the user's original report of a peer stuck "not syncing" — the message-truncation bug (bug 1, see above) meant this interaction between the checkpoint mechanism and MuHash activation had never actually been exercised until this session's activation-height tuning made both reachable together in regtest. It also sharpens the "Phase 2 deferred" note from the original fix report below: the gap wasn't just that the accumulator state isn't embedded in snapshot metadata for a faster bootstrap — the underlying *coin data itself* was silently wrong at every checkpoint once MuHash activation and the checkpoint interval overlapped.

Fix: moved the `WriteAutomaticSnapshot(...)` call from inside `ConnectBlock()` to `Chainstate::ConnectTip()`, placed right after `view.Flush()` (using `pindexNew`) so `CoinsTip()` — and therefore what `WriteAutomaticSnapshot()`'s own flush pushes into `CoinsDB()` — already includes the checkpoint block's own changes. `src/validation.cpp` only.

### Bug 9: deleting the old chainstate (bug 6's fix) broke `ChainstateManager::ValidatedChainstate()`, which unconditionally requires one to exist

Found while re-verifying bug 7+8's fixes across a node restart (the exact scenario from the user's second screenshot). The node no longer hit the "Assumeutxo data not found" fatal error, but crashed differently, deeper into startup:
```
Thread "b-initload" received signal SIGABRT
#5 ChainstateManager::ValidatedChainstate() at validation.h:1215
#6 StartIndexBackgroundSync() at init.cpp:2631
```
`ValidatedChainstate()` (`src/validation.h`) — used by `StartIndexBackgroundSync()` (`init.cpp`) and `BaseIndex::Init()` (`index/base.cpp`) — loops over `{CurrentChainstate(), HistoricalChainstate()}` looking for one with `m_assumeutxo == Assumeutxo::VALIDATED`, and calls `abort()` if it finds none. Normally that's always the primary (non-snapshot) chainstate, since `VALIDATED` is every `Chainstate`'s default value. ## 2026-07-02: mainnet-activation risk simulation, and bug 10 (VerifyDB silently corrupted the MuHash accumulator on every restart)

At the user's request: simulated what a real mainnet MuHash activation would look like, using regtest as a stand-in (the validation code path is identical; only chainparams differ). Two scenarios, both run against real, separately-built binaries — a "new" binary (this branch) and an "old" reference binary built from `16ef72f`, the commit immediately before MuHash was introduced (verified via `git merge-base main MuHash`).

### Scenario A: old software vs. new software across the activation height

Two nodes, connected throughout, synced identically up to height 49 (both algorithms agree pre-activation). At height 50 (regtest `MuhashAttestationActivationHeight`):
- Old-software-mined block 50 → rejected by the new-software node (`bad-utxo-attestation`), which also flags the old node `Misbehaving` and logs *"potential consensus incompatibility"*.
- New-software-mined block 50 → rejected by the old-software node, symmetrically.

Confirmed both directions: crossing a real activation height with *any* un-upgraded node present causes an immediate, silent hard fork — not an edge case, the deterministic outcome of a flag-day activation with mixed software versions on the network. This directly informed the user's plan to force upgrades via a version bump ahead of any real mainnet activation.

### Scenario B: does an updated node correctly rejoin the real chain afterward, and what happens to old vs. new coins?

Simulated: an old-software node mines its own (soon to be orphaned) blocks past the fork point while the "real" network (new software) mines further ahead with more work, then the node operator updates their software and reconnects. Live-verified with a real coinbase UTXO from *before* the fork and one *only on the abandoned branch*.

**First attempt exposed a new, serious, standalone bug (10) — unrelated to forks, hits every normal restart.** After updating and reconnecting, the node got stuck rejecting the real chain's block 50 with `bad-utxo-attestation`, *even though both sides were running identical new software*. Root cause: `CVerifyDB::VerifyDB()` (runs at every startup; regtest defaults `-checklevel=3`, verifying the last `-checkblocks` (default 6) blocks) disconnects those blocks against a throwaway, scratch `CCoinsViewCache` purely to sanity-check on-disk data — it never touches the real `CoinsTip()`/`CoinsDB()`, and at the default checklevel it disconnects *without* a matching reconnect (that only happens at `-checklevel>=4`). `Chainstate::DisconnectBlock()`'s MuHash bookkeeping had no way to tell this scratch call apart from a real reorg disconnect, so it permanently subtracted those blocks' coin changes from the **persistent** `m_utxo_muhash` accumulator on every single restart with more than 0 verifiable blocks — silently desyncing it from the chain's real tip. Confirmed directly: `gettxoutsetinfo muhash` (independent full-scan ground truth) at height 49 did not match what the corrupted accumulator produced after a restart.

Fix: added an `update_muhash` parameter (default `true`) to both `Chainstate::DisconnectBlock()` and `Chainstate::ConnectBlock()`. The two real call sites (`DisconnectTip()`/`ConnectTip()`, and `ReplayBlocks()`'s crash-recovery replay) keep the default; `CVerifyDB::VerifyDB()`'s two call sites (the level-3 disconnect check and the level-4-only reconnect check) now both pass `false`. Diagnosed with temporary `LogInfo` tracing added to `EnsureUTXOMuHashLoaded()`/`DisconnectBlock()` (rebuilt, reproduced, removed once confirmed) after an `fprintf(stderr, ...)` first attempt went missing — Bitcoin Core detaches/redirects stderr once its own logging takes over `-printtoconsole=0`, so anything logged after early startup needs `LogInfo`, not raw `fprintf`, to reliably land in `debug.log`.

**Re-verified after the fix**, correctly isolating test methodology from the bug itself (an old-software node that has *already* seen and rejected a peer's chain permanently caches that block as invalid regardless of a later software update — see below — so this needed a node that had *never* contacted the real network before updating, to observe a clean first attempt): fresh old-software node, mined its own 59-block chain in total isolation, gracefully stopped, restarted with the fixed new software, connected to the real (69-block) chain for the very first time — reorged cleanly to the exact matching tip, no `bad-utxo-attestation`, no crash.

### What happens to old vs. new coins (the user's original question)

With the same clean setup: the fully-reorged node correctly retains every pre-fork/shared coin (`gettxout` on a block-10-height coinbase: present, spendable, `confirmations: 60`) and correctly has **no record at all** of coins that only ever existed on the node's own abandoned branch (`gettxout` on the old-fork-only coinbase: empty/not found) — exactly matching the user's expectation: legitimate old coins are unaffected by the fork; coins mined only on the losing branch are simply gone, as if they never existed, once the node adopts the winning chain.

### Practical finding: a software update alone is not always enough

Separately verified a scenario the user didn't explicitly ask about but that matters for a real rollout: if an old-software node has **already** synced far enough to encounter and reject the new chain's blocks *before* being updated (which happens automatically and immediately over live P2P — essentially guaranteed for any node that was online), Bitcoin's block index permanently caches those specific blocks as `BLOCK_FAILED_VALID`. That marking survives a software update (it's data on disk, not a software limitation) and is **not** automatically cleared by upgrading alone — the node stayed stuck at the fork point even after the update, still logging `"...was previously marked invalid"` for the exact same blocks. `reconsiderblock <hash>` on the first rejected block partially helped but stalled again a few blocks later (several blocks had been marked invalid during the original rejection, not just one, and clearing them one at a time is impractical). `-reindex` reliably resolved it in one step (rebuilds the block index from the raw block files on disk, discarding all stale validity flags), reaching the exact same, fully-correct end state as the clean-first-contact case. **Operational implication for a real rollout: instruct operators to update *before* their node has a chance to sync past the activation height on the old chain if at all possible; if a node is found stuck after already having rejected blocks pre-update, `-reindex` (not just restarting) is the reliable fix, not `reconsiderblock`.**

## 2026-07-02 (follow-up: automatic recovery for nodes stuck on a rejected chain — replaces the `-reindex`-only fallback)

Direct follow-up to the finding immediately above: a software update alone doesn't unstick a node that already rejected the real chain pre-update, and the only remedy was manual `-reindex`. At the user's request, replaced that with fully automatic recovery, using the same automatic-snapshot-bootstrap machinery already hardened in the bug 1–10 fixes above — while explicitly reasoning about what this means at Elektron Net's much faster (60s vs Bitcoin's 600s) block time, and about a real security tradeoff surfaced mid-implementation. This took five rounds of live debugging to get end-to-end; each is recorded here rather than only the final state, since the failed intermediate steps are informative about how deep this particular class of bug goes.

**The feature.** `ChainstateManager::HasSustainedInvalidChainWithMoreWork()` (`src/validation.h`/`.cpp`): true when `m_best_invalid` — a chain we actually downloaded and attempted to validate, not a mere peer claim — carries enough more cumulative proof-of-work than our active tip to represent roughly **one hour** of blocks at this network's *own* block spacing (`Consensus::Params::nPowTargetSpacing`), not a fixed block count. This distinction matters concretely: Bitcoin Core's own analogous `LARGE_WORK_INVALID_CHAIN` warning hardcodes "6 blocks," which is about an hour at Bitcoin's 10-minute spacing — but Elektron Net's blocks arrive 10x faster (60s), so a flat "6" would only span ~6 minutes here: comfortably within ordinary propagation delay or a ordinary brief reorg, not evidence of a genuine, sustained problem. Converting the same real-world "about an hour" intent into blocks via `nPowTargetSpacing` keeps the meaning consistent regardless of how fast or slow blocks actually arrive — including if Elektron Net's block time is ever changed again in the future. Deliberately **not** wired into the existing `LARGE_WORK_INVALID_CHAIN` warning itself (`Chainstate::CheckForkWarningConditions()`, `src/validation.cpp`) — that stays exactly as upstream, hardcoded "6," because `test/functional/feature_notifications.py` pins that literal block count and message string; this is a separate, independently-tuned condition for a much more consequential action (discarding local chain state) than logging a warning.

**Round 1 — wire into the request path.** `PeerManagerImpl::MaybeRequestSnapshot()` (`src/net_processing.cpp`) previously only ran during ordinary IBD, and only requested a snapshot when the height gap to the best known header exceeded a full checkpoint interval. Bypassed both: a node stuck on a rejected chain isn't "behind" in the ordinary sense (its own doomed fork can keep it looking caught up by height), and normal reconnection/re-sync can't fix it regardless of gap size, since the peer's blocks right at the fork point are the ones being rejected.

**Round 2 — `m_best_header` is stuck too.** After round 1, nothing happened: `MaybeRequestSnapshot()` still exited immediately. Live-diagnosed: `getblockchaininfo` showed `"headers": 49` even though the real, competing chain was at height 250 (confirmed via `getchaintips`). `ChainstateManager::RecalculateBestHeader()` deliberately excludes any header descended from a `BLOCK_FAILED_VALID` ancestor — correct, upstream-inherited behavior in general, but it means `m_best_header` collapses back to no further than our own stuck tip precisely in the situation we're trying to recover from, since *every* header we know of past the fork point descends from the one block that failed. Added `ChainstateManager::BestInvalid()` (public accessor for the existing protected `m_best_invalid`) and used it instead of `m_best_header` as the reference chain when stuck, to correctly compute the target checkpoint height.

**Round 3 — the download worked, activation didn't run at all.** With rounds 1–2, the snapshot was correctly requested and downloaded (confirmed in `debug.log`: `"[snapshot] Download complete..."`). But it just sat on disk. `MaybeActivateAutomaticSnapshot()` (`src/init.cpp`) — a *separate* function on its own 30-second scheduler — had its own, independent `if (!chainman.IsInitialBlockDownload()) return;` gate, for the same underlying reason as round 1's problem. Bypassed the same way.

**Round 4 — `ActivateSnapshot()` refuses a checkpoint on a chain we've marked invalid.** With round 3 fixed, activation was attempted but failed: `"The base block header (...) is part of an invalid chain"`. This is `ActivateSnapshot()` (`src/validation.cpp`) correctly refusing to load state for a chain the node has already determined, through its own validation, to be invalid — a real, deliberate safety check, not a bug. But that's exactly the *stale* determination (made by old, pre-upgrade software under different rules) that a stuck node needs to get past. Added a `stuck_on_invalid_chain`-gated call to `Chainstate::ResetBlockFailureFlags()` — the same underlying mechanism the `reconsiderblock` RPC uses — right before `ActivateSnapshot()`, clearing the stale `BLOCK_FAILED_VALID` marking on the checkpoint (and its ancestors/descendants) rather than trying to activate against a chain the node itself has marked unusable.

**Round 5 — clearing the flag didn't update `m_best_header`.** Round 4's fix still failed, now with `"A forked headers-chain with more work... exists. Please proceed to sync without AssumeUtxo."` — `ActivateSnapshot()` requires the checkpoint to be an ancestor of `m_best_header`, but clearing one block's failure flag doesn't itself trigger a recompute of `m_best_header` (same underlying issue as round 2, now hit a second time from a different angle). Added a `chainman.RecalculateBestHeader()` call immediately after `ResetBlockFailureFlags()`.

**Final live verification** (all five fixes together): node-new mined to height 250 (checkpoints at 100 and 200 available); node-old (a genuinely fresh, pre-MuHash-software node, from the `16ef72f` reference build described earlier) connected to it for the first time, synced compatibly to height 49, then correctly rejected node-new's MuHash-based blocks from height 50 onward, permanently caching them `BLOCK_FAILED_VALID` — exactly the "already rejected before updating" scenario from the entry above. Updated to the fixed new software and reconnected: **with zero manual RPC calls this time** (no `reconsiderblock`, no `-reindex`), the node requested a snapshot, downloaded it, cleared the stale marking, recomputed its header state, and activated — reaching height 250 with a `bestblockhash` byte-for-byte identical to node-new's, fully automatically, within a few scheduler cycles.

**Security discussion (recorded here because it changed the design, and to leave the tradeoff visible for future review).** Partway through this work, the user raised a specific, well-founded concern: does automatically clearing `BLOCK_FAILED_VALID` markings based on "the other chain has substantially more work" weaken a deliberate Bitcoin Core safety property? Confirmed directly: yes, this concern is well-founded, and it's worth being precise about *why*. `reconsiderblock` being a manual-only RPC (and Bitcoin Core never automating "trust whichever chain has more work over a rejected one") is genuine, old, upstream design — it predates snapshots/assumeutxo entirely. The reasoning: cumulative proof-of-work proves computation was spent, not that the resulting chain is honest — an attacker with sufficient hashpower can produce a chain with "more work" that is fraudulent (e.g. an inflation bug), and a node that automatically abandons its own, *correct* rejection of that chain the moment it accumulates enough work would side with the attacker. Elektron Net's *automatic* snapshot-bootstrap machinery (no RPC, no human step, unlike upstream's manual `loadtxoutset`) is what newly exposes this decision to that risk — in upstream Bitcoin Core the question never arises because a human always has to run the command. The mitigating factor this feature does have — the snapshot's UTXO content is independently cross-checked against that chain's own on-chain MuHash coinbase attestation before being trusted — is real, but incomplete: it only proves the snapshot data is *internally consistent* with the chain it came from, not that the chain itself represents honest, correct history. A self-consistent-but-fraudulent chain from a sufficiently well-resourced attacker would still pass that check.

Given this, a narrower alternative was proposed: gate the automatic recovery specifically on the *reason* the chain was rejected being `bad-utxo-attestation` (a pure consensus-parameter/activation-height mismatch — exactly what an outdated-but-honest client produces) rather than any rejection reason at all (which would also fire for, say, forged signatures or invalid coin creation — signals much more indicative of a genuine attack than of a stale software version). This would require additionally tracking the specific reject reason alongside `m_best_invalid` (not currently persisted — `CBlockIndex::nStatus` only records coarse validity, not why). **The user was asked directly and chose to keep the broader trigger for now**, accepting the tradeoff explicitly, on the basis that Elektron Net's current, very small operator count makes the practical risk low today. This is intentionally recorded here, not glossed over: **worth revisiting — narrowing to a `bad-utxo-attestation`-specific trigger — if and when the network grows toward the scale the user has explicitly said they're planning for.**

**`m_best_header` call-site survey.** Before landing on the round-2/round-5 fixes, all ~30 other call sites of `m_best_header` across the codebase were checked for the same "collapses to the node's own tip when the entire known alternative is invalid" behavior, to see whether this was a narrow issue or symptomatic of something wider. Found exactly one genuinely analogous case: `awaiting_snapshot_bootstrap` in `PeerManagerImpl::SendMessages()` (`net_processing.cpp`), an existing, separate check for whether to hold off historical-block download requests while a snapshot bootstrap might be needed — it has the identical latent limitation, but its effect there is simply staying inactive in the stuck-chain scenario (no incorrect behavior, just no help — which is exactly the gap this whole feature fills). Every other call site is either a display/RPC field (`getblockchaininfo`'s `"headers"`, GUI sync progress — arguably correct to show a conservative number here, and the separate `LARGE_WORK_INVALID_CHAIN` warning already flags the underlying problem through a different channel) or a minor block-relay/pruning-target heuristic, not a correctness issue. `ChainstateManager::IsInitialBlockDownload()` was specifically checked too, since this feature's own gating logic depends on it — confirmed it does **not** depend on `m_best_header` at all (only the active chain's own tip age/work), so it isn't affected by any of this.

## 2026-07-02 (follow-up: narrowing the automatic-recovery trigger, and two more bugs found finishing it)

Direct follow-up to the "Security discussion" above. The user reconsidered and asked to adopt the narrower, consensus-specific trigger after all, then asked for it to be live-tested the same way as everything else in this document. Two further implementation attempts, and two additional bugs surfaced while verifying the second one, are recorded below.

### Narrowing attempt 1 (reject-reason tracking) — architecturally unworkable, fully reverted

First approach: thread the specific rejection reason (`bad-utxo-attestation` vs. anything else) through to `m_best_invalid`, so the trigger could require that exact reason rather than "any invalid chain with more work." Added a `reject_reason` parameter to `InvalidChainFound()`/`InvalidBlockFound()` and a new `m_best_invalid_reject_reason` field on `ChainstateManager`.

This does not work, for a reason that only became apparent by tracing every place `m_best_invalid` gets set, not just the one this session's rounds 1–5 had touched: `BlockValidationState` (which carries the reject reason) is **never persisted to disk** — it is transient, in-memory, tied to one specific validation attempt. `m_best_invalid` itself is set from **three** separate places, not one: `Chainstate::InvalidChainFound()` (a fresh validation failure, reason available), `FindMostWorkChain()` (rediscovering an already-known-invalid block while walking candidate ancestors, no fresh reason), and — critically — `ChainstateManager::LoadBlockIndex()`, which rebuilds `m_best_invalid` **at every node startup** purely from persisted `CBlockIndex::nStatus` bits (`BLOCK_FAILED_VALID`), with no reason data available at all. This is exactly the scenario this whole feature targets — a node restarting with fixed software after having rejected a chain — so the one case that mattered most is precisely the one where a reason-based trigger would always see "no reason recorded" and refuse to fire. Reverted in full: the field, the constructor parameter, and all associated tracing removed; `InvalidChainFound()`/`InvalidBlockFound()` restored to their original signatures.

### Narrowing attempt 2 (height-based) — shipped

Replaced the reason check with a structural one that doesn't depend on transient, unpersisted state: `ChainstateManager::HasSustainedInvalidChainWithMoreWork()` now additionally requires `m_best_invalid->nHeight >= GetConsensus().MuhashAttestationActivationHeight` (and that activation is even enabled on this network, i.e. not `-1`). This captures the same intent the user asked for — don't treat *any* invalid-chain-with-more-work claim as grounds for automatic recovery, only ones that are structurally consistent with "this is a stale pre-upgrade client rejecting a chain solely because of the MuHash consensus change" — without needing the specific reject reason at all: a chain that diverges only *before* the activation height couldn't have been rejected for a MuHash-related reason in the first place (the dual-algorithm logic doesn't even engage below that height), so requiring the rejected chain to extend past the activation height is a reason-independent proxy that happens to survive exactly the restart case that broke attempt 1. This is strictly narrower than the original trigger (a plain "any invalid chain with more work" claim below the activation height no longer qualifies) while remaining robust to the one thing that mattered: it only reads data that is actually persisted.

### Bug 11: the recovered node activated the snapshot but never downloaded the remaining post-checkpoint blocks

Live-verifying the height-based narrowing end-to-end (same setup as the "Final live verification" above: old-software node stuck at height 49 after rejecting node-new's chain, updated to new software, reconnected) surfaced a new problem: the snapshot correctly activated at the checkpoint (height 200), but the node then sat there indefinitely — `getblockchaininfo` stuck at `"blocks": 200` although `"headers": 250` was already correctly known, and `getpeerinfo` showed `synced_headers: -1, synced_blocks: -1` with an empty `inflight` queue: the node knew about the remaining blocks but was never asking its peer for them.

Root cause, found by tracing `debug.log`: `AcceptBlockHeader()` (`src/validation.cpp`) rejects an entire incoming `headers` message outright — via the pre-existing `duplicate-invalid`/`bad-prevblk` checks — the moment it contains a header for a block already cached `BLOCK_FAILED_VALID` in the local index (exactly block 50, from the original pre-update rejection). Meanwhile, headers sync with any one peer only ever *starts* once per connection under normal Bitcoin Core behavior (`CNodeState::fSyncStarted` latches `true` and stays that way; the only built-in reset path requires *another*, better-connected peer to fail over to — which a small, young network, or this two-node test, does not have). The combination is a permanent, self-inflicted deadlock at the P2P layer: the very first (and only) headers exchange after reconnecting ran into the stale `BLOCK_FAILED_VALID` marking and aborted, `fSyncStarted` stayed `true` forever after that single failed attempt, and nothing ever prompted a retry — including our own stuck-chain recovery, which clears the stale marking (see round 4 above) but had no way to know a peer's headers sync needed to be redone once that marking was gone.

Fix: added `PeerManager::ResyncHeadersAfterRecovery()` (new virtual method, implemented in `PeerManagerImpl`), called once from `init.cpp`'s `MaybeActivateAutomaticSnapshot()` immediately after a stuck-chain-recovery activation succeeds. It resets `fSyncStarted` (and decrements `nSyncStarted`) for every peer that had already given up, so the normal `SendMessages()` logic naturally re-sends a fresh `getheaders` on its next pass — this time succeeding, since the stale marking is already cleared by that point.

### Bug 12: the bug 11 fix itself deadlocked the entire scheduler thread

First implementation of `ResyncHeadersAfterRecovery()` locked `g_msgproc_mutex` before `cs_main`, mirroring the lock order used by `PeerManagerImpl::SendMessages()` — reasonable-looking, but wrong for the caller. Live-tested and found: the node's scheduler thread (where `MaybeActivateAutomaticSnapshot()` runs, on its 30-second timer) hung permanently the moment it reached that `LOCK(g_msgproc_mutex)` call — confirmed with temporary `LogInfo` tracing bracketing each lock acquisition, which showed execution reaching "about to lock g_msgproc_mutex" and never printing anything after it, on every subsequent scheduler tick (the whole thread, not just this one call, was wedged — no further `[snapshot]`-tagged scheduled work ran afterward either).

Root cause: `CConnman::ThreadMessageHandler()` (`src/net.cpp`) acquires `g_msgproc_mutex` **once**, before entering its processing loop, and holds it for the net thread's entire lifetime — it is not released and reacquired between message-processing cycles the way a first read of the code might suggest, only released at shutdown. `SendMessages()`'s `EXCLUSIVE_LOCKS_REQUIRED(g_msgproc_mutex)` annotation is correct for that function precisely because its *only* caller already holds the lock permanently for as long as the net thread runs — but that means no other thread can ever successfully acquire `g_msgproc_mutex` during normal operation, making it the wrong lock to reach for from anywhere outside that one thread.

Fix: `fSyncStarted` and `nSyncStarted` (the two fields actually being modified) are guarded by `cs_main`, not `g_msgproc_mutex` — a general-purpose, already-safe-to-take-from-any-thread lock used throughout the codebase, including by this feature's other cross-thread calls into validation state. Rewrote `ResyncHeadersAfterRecovery()` to lock only `cs_main`. The one field that *is* `g_msgproc_mutex`-guarded, `Peer::m_headers_sync_timeout`, is deliberately left untouched by this function instead of also being reset: it is unconditionally overwritten by the net thread itself, under its own already-held lock, the next time it starts a headers sync for that peer — so leaving a stale value behind between the reset and the next sync attempt is harmless, and touching it here was never actually necessary. Removed all temporary tracing once confirmed.

**Final live verification** (attempt 2's height-based narrowing, plus bugs 11 and 12's fixes, all together, three full end-to-end reruns of the recovery scenario across this sub-session — the first surfaced bug 11, the second surfaced bug 12, the third succeeded cleanly): old-software node stuck at height 49 after rejecting node-new's real chain from height 50 onward (`BLOCK_FAILED_VALID` cached, exactly the "already rejected before updating" scenario); gracefully stopped and restarted with the fixed new software; reconnected. With zero manual intervention, `debug.log` shows the complete chain of events in order — snapshot requested, downloaded, stale marking cleared (`"Clearing stale invalid marking on ... before activation"`), activated at height 200, headers sync reset for the peer (`"Resetting headers sync state for peer=0 after stuck-chain recovery."`), and the node reaching **height 250 with a `bestblockhash` identical to node-new's**, `getpeerinfo` correctly showing `synced_headers: 250, synced_blocks: 250`. Full unit test suite (`elektron_simulation_tests`) re-run afterward: only the already-known, unrelated `prune_depth_calculation` failure remains.

### Security scoping — final state

The trigger is now scoped to `m_best_invalid->nHeight >= MuhashAttestationActivationHeight`, replacing the original "any invalid chain with more work" condition the user had initially chosen to keep. This is narrower in exactly the way the user asked for — a chain that only diverges before the activation height can no longer trigger automatic recovery at all, regardless of how much more work it carries — while avoiding the specific trap that made the reject-reason approach (attempt 1) a dead end: `BlockValidationState` is transient and never persisted, so any design relying on "why was this rejected" silently stops working across the one event this feature exists to survive — a node restart with updated software. The height-based check reads only data (`CBlockIndex::nHeight`, `Consensus::Params::MuhashAttestationActivationHeight`) that is either persisted to disk or a compile-time/chainparams constant, so it behaves identically whether the invalid chain was just discovered in this process's lifetime or rebuilt from disk at the last `LoadBlockIndex()` call — the scenario that matters most in practice.

## 2026-07-02 (follow-up: a node falling behind a pruning peer's horizon, and a chain of four bugs found fixing it)

Reported by the user via real testing of the Windows GUI client (not regtest scripting): two nodes, `addconnection "<addr>" "outbound-full-relay" true` (not `-connect`, which is exempt from most disconnect/misbehavior handling — this matters, see below), node1 mining ahead while node2 was offline for a while. On reconnecting, node2's sync progress bar and peer traffic graph showed a live connection with data flowing, yet `getblockchaininfo` never advanced. Diagnosed collaboratively over several rounds — including the user directly testing `listunspent` behavior on immature self-mined coins (correctly explained as ordinary `COINBASE_MATURITY` behavior, unrelated to the underlying bug) and confirming via `getpeerinfo`/the network-traffic graph that the connection itself was healthy — before landing on the real cause below. Reproduced and fixed against a local regtest pair using the user's exact connection method throughout, per their explicit request to keep the fix minimal and not overcomplicate it.

### The scenario: ordinary sync, not a fork

Unlike the MuHash stuck-chain-recovery work above, this has nothing to do with invalid chains, `BLOCK_FAILED_VALID`, or the security tradeoff discussed there. node2's headers synced perfectly (`getblockchaininfo` correctly showed `"headers": 665` against node1's real tip) — only the *block data* was the problem: node2 had been offline long enough that node1, a pruned node, had already deleted (`pruneheight` advanced past) the blocks node2 still needed. `PeerManagerImpl::MaybeRequestSnapshot()` (net_processing.cpp) is the mechanism that exists precisely for this — bootstrap from a newer checkpoint instead of trying to fill the gap block-by-block — but it only ran during ordinary IBD or (from the work above) while stuck on an invalid chain. A node that had already left IBD once (`IsInitialBlockDownload()` latches `false` permanently per node lifetime, by design) and simply fell behind afterward hit neither condition, so the function returned immediately, every single time, forever. Confirmed live and independently reproduced in this session's own regtest: repeated `"Timeout downloading block ..., disconnecting peer"` entries — the node kept trying to fetch individual already-pruned blocks, timing out, and (since `addconnection`-added peers are not automatically retried) staying disconnected until manually reconnected.

### Fix 1: `ChainstateManager::HasFallenBehindPruneHorizon()`

New method (validation.h/.cpp) alongside the existing `HasSustainedInvalidChainWithMoreWork()`: true when the best known header is at least one full checkpoint interval (`Consensus::Params::MandatoryPruneDepth`) ahead of the active tip — mirroring the exact height-gap math `MaybeRequestSnapshot()` already used internally for the ordinary-IBD case, just exposed as a reusable, `cs_main`-lockable check. Added as a third bypass condition alongside `ibd`/`stuck_on_invalid_chain` in both `PeerManagerImpl::MaybeRequestSnapshot()` (net_processing.cpp) and `MaybeActivateAutomaticSnapshot()` (init.cpp). Deliberately independent of the MuHash-specific narrowing above — a chain-validity signal has no bearing on "am I simply too far behind," and vice versa.

The genuinely minimal part: `MaybeRequestSnapshot()` already contained the "is my existing snapshot behind the latest checkpoint? request a newer one" logic, and `MaybeActivateAutomaticSnapshot()` already contained the "is the downloaded snapshot newer than what's active? replace it" logic — both written in earlier work, both correct, neither ever reachable until this one gate was loosened. No other new mechanism was needed for the trigger itself.

### Bug 14: the "replace an existing snapshot" path had never actually been exercised — and crashed

Live-testing the new trigger (node2 stuck at a stale height-300 snapshot, node1 having since advanced to 550 with `pruneheight` 433) surfaced a second, previously-dormant bug: the process died silently the moment it tried to replace the old checkpoint-300 snapshot with the new checkpoint-500 one — no log line, no stack trace, `debug.log` just stopped mid-sequence.

Root cause: `ChainstateManager::ActivateSnapshot()`'s pre-existing "automatic snapshots may replace an existing snapshot chainstate" branch deleted the old snapshot chainstate — both its on-disk data and its entry in `ChainstateManager::m_chainstates` — immediately, *before* the new chainstate existed to take its place. That leaves `m_chainstates` completely empty for everything in between. `ChainstateManager::CurrentChainstate()` calls `abort()` by design when it finds no matching chainstate (a deliberate invariant-enforcing crash, not a bug in itself) — and the very next line, the ordinary pre-existing mempool-emptiness check already in `ActivateSnapshot()`, called exactly that.

Fix: restructured so the old chainstate's coins views are reset early — required regardless, since `Chainstate::StoragePath()` is a *fixed* path shared by every snapshot generation (never parameterized by checkpoint), so the old leveldb handle must release its lock before a new one can open at the same path — but the old chainstate itself stays in `m_chainstates` as a harmless "zombie" (everything that runs on it in that window, like the pre-existing cache-resizing code, only touches header-chain state, not coins views) until immediately after `ChainstateManager::AddChainstate()` registers the new chainstate and demotes the old one via the exact same target-block mechanism used for the original IBD-chainstate-to-snapshot transition. Only then is the old chainstate actually removed from the list, via `ChainstateManager::RemoveChainstate()` — list-only, no second disk-delete attempt (which would otherwise hit the *new*, just-activated chainstate's identical on-disk path and destroy it). Also switched `Chainstate::InitCoinsDB()`'s `should_wipe` parameter to `true` for the replacement case, letting leveldb itself atomically discard the old checkpoint's data as part of opening the new database at the same path, instead of a separate manual pre-deletion step. Added one small defensive guard to `ChainstateManager::MaybeRebalanceCaches()` (skip if the current chainstate's coins views are null) for the one remaining edge case this restructuring can't fully close — if snapshot *population* itself fails partway through a replace (e.g. a corrupted download), the old chainstate is unrecoverable regardless, since its data was already folded into the new (now-failed) database open. Explicitly accepted as a narrow, known limitation rather than engineered further, matching the user's explicit request to keep this fix minimal.

### Bug 15: fixing Bug 14 immediately surfaced a third issue — stale in-flight block requests

Same live test, next round: node-old jumped cleanly from height 300 to 500 via the now-fixed replace path — then sat completely motionless instead of continuing on to node1's tip (550). `getpeerinfo` showed `synced_headers: 550` (correct) but `synced_blocks: 300` (stale). Root cause: 16 blocks (301–316 — exactly `MAX_BLOCKS_IN_TRANSIT_PER_PEER`) had been requested from the peer against the *pre-snapshot* chainstate right when the fell-behind trigger first fired, and were still sitting in that peer's in-flight tracking (`CNodeState::vBlocksInFlight` / `PeerManagerImpl::mapBlocksInFlight`) after the snapshot jump superseded them. `FindNextBlocksToDownload()` refuses to issue new requests once a peer's in-flight count is already at the maximum, so real progress silently stalled — confirmed live, roughly five minutes later one of those stale requests finally hit the ordinary block-download timeout and disconnected the peer, reproducing the *exact* `"Timeout downloading block ..., disconnecting peer"` signature from the user's original report. Since a peer added via `addconnection` does not reconnect on its own (established earlier with the user), the node would have simply stayed disconnected from there.

Fix: new `PeerManager::ClearBlocksInFlight()` (net_processing.h/.cpp), built entirely on the existing, already-battle-tested `RemoveBlockRequest()` — just called for every currently in-flight hash instead of one at a time. Called from `init.cpp` right after *every* successful snapshot activation, deliberately unconditional rather than scoped to just the two recovery-trigger cases: a large first-time bootstrap can just as easily have genuinely in-flight blocks against the pre-snapshot chainstate at the moment it activates.

### Bug 16: fixing Bug 15 immediately surfaced a fourth issue — a stale `m_chain_tx_count`

Re-running the same live test end to end one more time: node-old crashed again, this time with a plain, informative `assert()` (not a silent `abort()`) caught in the process's stderr: `ChainstateManager::CheckBlockIndex(): Assertion '(pindexFirstNeverProcessed == nullptr || pindex == snap_base) == pindex->HaveNumChainTxs()' failed`. Root cause: the *old* checkpoint's base block (height 300) had `m_chain_tx_count` set to a lower-bound estimate back when it was activated as its own generation's `snap_base` (see Bug 7, earlier in this document — the fix that made automatic/dynamic snapshots, which have no static assumeutxo chainparams entry, report verification progress at all). Replacing it with the newer checkpoint-500 snapshot never cleared that now-stale value, so `CheckBlockIndex()` — which runs after every newly-connected block under regtest's default `-checkblockindex` settings — found a block with `HaveNumChainTxs() == true` that was no longer the *current* `snap_base`, violating the invariant on the very first block processed after the replace succeeded.

Fix: in `ActivateSnapshot()`'s replace branch, alongside resetting the old chainstate's coins views, explicitly reset the old `snap_base` block index's `m_chain_tx_count` back to `0`.

### Final live verification (all four fixes together)

node-old stuck at height 300 on a stale (pre-outage) datadir, reconnected via `addconnection "..." "outbound-full-relay" true` — the user's exact real-world connection method, not `-connect` — to a node-new that had since advanced to height 550 with `pruneheight` 433 (pruning away everything node-old still needed). Automatically, with zero manual RPC calls, zero crashes, and zero stalls: detected it had fallen behind, requested and downloaded a newer checkpoint-500 snapshot, replaced its existing (stale) snapshot chainstate cleanly, immediately continued downloading the remaining blocks, and reached node-new's exact tip (`bestblockhash` byte-for-byte identical). Full unit test suite (`elektron_simulation_tests`) re-run afterward: only the already-known, unrelated `prune_depth_calculation` failure remains.

## 2026-07-02 (follow-up: wallet balances silently lost after restoring `wallet.dat` onto a resyncing node)

Reported by the user via real Windows GUI testing: a wallet on node2 held 10 mined coinbase outputs; `wallet.dat` was backed up, then node2's entire datadir was wiped, restarted fresh, and the backup restored. The GUI showed all 10 transactions with a "?" confirmation icon and a balance of exactly `0.00000000 ELEK`, even after closing and reopening the client. The user correctly diagnosed the expected behavior themselves: *"Die Bestände sollten doch per UTXO Scan wiederherstellbar sein"* — referencing the pre-existing `CWallet::ScanUTXOSet()` pocket-recovery mechanism documented in §2.6 of `BITCOIN_CORE_DIFF.md`. A follow-up round (deleting and re-importing the wallet a second time) produced a wildly incorrect balance (~480,000,000 ELEK) instead of either `0` or the correct value; closing and reopening the client once more then showed the correct `0.19531250 ELEK` (exactly 10 × the known per-output amount). Reproduced live on regtest (`MandatoryPruneDepth = 100`, so the checkpoint/snapshot cycle is reachable in seconds rather than requiring mainnet's 197,280 blocks) using the wallet-enabled build (`-DENABLE_WALLET=ON -DENABLE_IPC=OFF`, disabled by default in the existing build tree).

### Root cause 1: `ScanUTXOSet()` runs exactly once, at wallet-load time, and can lose the race against asynchronous snapshot bootstrap

`CWallet::AttachChain()`'s pruned-node fallback (§2.6) calls `ScanUTXOSet()` synchronously while the wallet is loading — but automatic snapshot bootstrap (request/download/activation) runs on a separate 30-second scheduler (`MaybeActivateAutomaticSnapshot()`, `init.cpp`) that can still be in progress, or not yet started, at that exact moment. On a freshly wiped node this is the common case: the wallet loads while the node is still at genesis, `ScanUTXOSet()` sees an empty UTXO set (finds nothing), and `AttachChain()` unconditionally records the wallet as caught up to the current (essentially pre-sync) tip. Nothing ever re-triggers `ScanUTXOSet()` afterward — restarting the client with no new blocks in between changes nothing, since the wallet's persisted best-block locator still matches. Live-reproduced exactly: restoring `wallet.dat` immediately after a fresh node start left the 10 coinbase transactions in `mapWallet` (visible in `listtransactions`, category `orphan`, `abandoned: true` — the "?" icon) but contributing `0` to `getbalances`.

There is a second, narrower path into the same dead end even when a rescan *is* attempted: on a wallet restored right at height 0, `AttachChain()`'s outer gate (`tip_height != rescan_height`) can itself evaluate as "nothing to do" — the wallet's locator fork point and the node's current (genesis-only) tip are both height 0 — so the pruned-fallback branch containing `ScanUTXOSet()` is never even entered in the first place.

**Fix** (`src/wallet/wallet.cpp`, `src/wallet/wallet.h`): new `CWallet::m_utxo_scan_needs_retry_after_snapshot` flag, set unconditionally near the top of `AttachChain()` whenever `chain.isInitialBlockDownload()` is true at wallet-load time — deliberately independent of whether the rescan-height gate decides an immediate scan is needed, so it also covers the height-0 case above. New `CWallet::MaybeRescanUTXOSetAfterSnapshot()` re-runs `ScanUTXOSet()` (idempotent — see root cause 2 below for why that's now safe) and clears the flag if it succeeds. Wired up via a new `interfaces::WalletLoader::rescanUTXOSetIfNeeded()` method (implemented in `src/wallet/interfaces.cpp` by calling the above on every loaded wallet), called from `init.cpp`'s `MaybeActivateAutomaticSnapshot()` immediately after every successful snapshot activation — the same hook point already used for `ClearBlocksInFlight()`/`ResyncHeadersAfterRecovery()` (see the entry above). `node::NodeContext::wallet_loader` is always safe to call through from `init.cpp` (a pure interface pointer, null when the wallet component is disabled), so this needed no `ENABLE_WALLET`-conditional code in `init.cpp` itself.

### Root cause 2: a dangling reference in the wallet's output cache, explaining the ~480,000,000 ELEK reading

`WalletTXO` (`src/wallet/transaction.h`) stores plain `const CWalletTx&` / `const CTxOut&` references, the latter pointing directly into a `CWalletTx`'s current `tx->vout` array. `CWallet::RefreshTXOsFromTx()` populated the `m_txos` cache from these references — but on an outpoint it had already cached once, it silently did nothing on every subsequent call (`if (m_txos.contains(outpoint)) { } else { ... }`). Meanwhile `CreditUTXOFromChain()` (used by both the original and the retry-triggered `ScanUTXOSet()` pass) *replaces* an existing `mapWallet` transaction's underlying `CTransaction` object via `wtx.SetTx()` when re-crediting an outpoint it already knew about by txid — which is exactly what happens on a second `ScanUTXOSet()` pass over transactions a first, incomplete pass had already partially recorded. Once the old `CTransaction` object's refcount drops to zero, any `WalletTXO` entry still referencing its `vout` array is left pointing at freed memory. Reading `nValue` back out of that freed memory produces whatever garbage happens to occupy it — a plausible, exact explanation for a balance reading like ~480,000,000 ELEK instead of a small integer multiple of the real balance (which is what a double-counting bug would have produced instead). This also explains why the very next restart "fixed" it: `m_txos` is a runtime-only cache, rebuilt from scratch (from the now-consistent on-disk wallet state) on every wallet load.

**Fix** (`src/wallet/wallet.cpp`): `RefreshTXOsFromTx()` now always erases and re-inserts the `m_txos` entry (`m_txos.erase(outpoint); m_txos.emplace(...)` — `WalletTXO` has no assignment operator, since it holds reference members, so `insert_or_assign` is not an option), keeping the cache pointed at the wtx's *current* `tx`/`vout` unconditionally rather than only on first sight. This is the same code path used by `AddToWallet()`'s existing new-or-updated-transaction handling, so the fix is general, not `ScanUTXOSet()`-specific.

### Live verification (all three previously-observed states)

Using the wallet-enabled regtest build: created a wallet on node2, mined 10 blocks to it on node1 (regtest checkpoint interval 100), matured and confirmed a `50 ELEK` balance normally, backed up `wallet.dat`, mined 200 further blocks on node1 (crossing two checkpoints so the original blocks are pruned and a new automatic snapshot exists), then reproduced each of the three reported states against a completely wiped, freshly started node2:

1. **Wallet restored at height 0 (racing snapshot bootstrap):** `getbalances` immediately read `0`, the 10 transactions showed as `orphan`/`abandoned` — matching the original report exactly. Once the automatic snapshot activated a few scheduler ticks later, `debug.log` showed the new retry firing unprompted (`"Re-scanning UTXO set after snapshot activation (previous scan ran before the node was fully synced)..."`, `"UTXO scan credited 10 outputs"`), and `getbalances` read the correct `50 ELEK` with no manual RPC calls or client restart — the exact class of fix the user asked for ("UTXO scan should be able to recover this").
2. **Deleting and re-importing the wallet a second time, now that the node is fully synced:** immediately correct (`50 ELEK`), matching the user's own follow-up observation *("Wenn node2 sync ist und ich danach mein wallet restore mache, ist alles korrekt")* — this case never depended on the fix, it already worked, and continues to.
3. **Plain client restart after recovery:** balance stayed stable and correct across a full daemon stop/start cycle.

Built a second, wallet-enabled test binary (`-DENABLE_WALLET=ON -DBUILD_TESTS=ON -DENABLE_IPC=OFF`) to check for regressions, since the repository's primary build tree has the wallet disabled. Ran `wallet_tests`, `wallet_transaction_tests`, `walletload_tests`, `coinselector_tests`, `ismine_tests`, and `elektron_simulation_tests` both with and without this pass's changes (`git stash`/`pop` on the touched files) to isolate cause from pre-existing baseline: 13 wallet-suite failures (subsidy-amount and mempool-broadcast assertions unrelated to this change) and the already-known `prune_depth_calculation` failure are present identically in both runs — this pass introduces no new test failures.
